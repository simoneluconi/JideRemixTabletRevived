# LineageOS 21 bring-up notes

Working notes for the first LineageOS 21 (Android 14) builds on the Jide Remix Ultra Tablet (sk1wg). They record what was measured and decided, so the next steps do not have to re-derive it.

## Trees

| Path (in `~/android/lineage-sk1wg`) | What |
|---|---|
| LineageOS-UL `lineage-21.0` | Base, synced with [`manifests/sk1wg.xml`](../manifests/sk1wg.xml) and [`manifests/zz-lineage-snapshot.xml`](../manifests/zz-lineage-snapshot.xml) (Galaxy Camera Revived's, same file; UL froze on 2025-04-04). Build steps: [TECHNICAL.md](TECHNICAL.md) |
| `kernel/jide/sk1wg` | Our kernel, branch `sk1wg` (see "Kernel" below). A local clone for now, to become a public GitHub fork |
| `device/jide/sk1wg` | The device tree (git repo, branch `lineage-21.0`) |
| `vendor/jide/sk1wg` | Generated by `extract-files.sh` from the stock 2.0.305 `/system`; never committed |

The tree is separate from the Galaxy Camera's `~/android/lineage` (it borrows its git objects with `repo init --reference`), so the two builds never share an `out/`.

## Kernel

NVIDIA's 3.4 macallan kernel, from the community CM13 port (TerenceWSK `cm-13.0`, 3.4.112), plus:
- Android 8+ backports from LineageOS's Shield Portable kernel (roth `lineage-15.1`): binder with the 64-bit ABI and binder/hwbinder/vndbinder, seccomp-bpf with TSYNC, no_new_privs, ambient capabilities, the new UID routing (FRA_UID_RANGE).
- From html6405's Exynos 3.4 kernel: getrandom, memfd_create, `sk_uid` and UID-based routing in the IP protocols, ARM 8-byte `get_user()`.
- Ours: syscall wiring, Android cpuset `allow_attach` and cpus kept across CPU hotplug (cpuquiet), the `rt_fill_info()` NULL fix, `sk_fullsock()`, `CONFIG_CMDLINE_EXTEND` for FDT boots.
- Defconfig `lineageos_sk1wg_defconfig`. It appends `androidboot.hardware=macallan androidboot.boot_devices=sdhci-tegra.3 androidboot.selinux=permissive` to the bootloader's command line.

An independent review (2026-11-06) found the RTM_GETROUTE oops and the missing socket UIDs; both are fixed. Still open, not needed to boot: SELinux binder hooks, `RTA_MARK` in the route policies, renameat2, eBPF.

Stock Remix OS uses the 32-bit binder ABI: to boot it on our kernel (a regression test), build with `CONFIG_ANDROID_BINDER_IPC_32BIT=y`.

## Graphics

NVIDIA's T114 blobs from Remix OS 2.0.305 (Android 5.1):
- **Link check against Android 14** (the Galaxy Camera's 32-bit LOS21 libraries): the 25-library closure of EGL/GLES/gralloc/hwcomposer only misses `android_atomic_{inc,dec,acquire_load,release_store}` (gralloc, hwcomposer) and one `GraphicBuffer` constructor (hwcomposer). Shims: `shims/atomic.c`, `shims/graphicbuffer.cpp`, wired with `TARGET_LD_SHIM_LIBS`.
- No text relocations in any of them.
- The EGL/GLES wrappers have `/system/lib/` built in; `extract-files.sh` rewrites it to `/vendor/lib/` (same length).
- `gralloc.tegra.so` has **no framebuffer device**, so the HWC2-on-fb fallback cannot work with it; the display needs `hwcomposer.tegra.so` (HWC 1.x) through `hwc2on1adapter`.
- `hwcomposer.tegra.so` uses `GraphicBuffer` in one place, `create_graphic_buffer()`: `operator new(128)` then the 5.1 constructor. Android 14's `GraphicBuffer` is **160 bytes** on 32-bit ARM, so `extract-files.sh` patches `movs r0, #128` at file offset 0xc11c to `#160` (Thumb `8020` -> `a020`, one byte). The shim builds Android 14's object there and `static_assert`s the size. Checked with the tree's compiler: the rest of what the blob touches is unchanged since 5.1 (it calls `RefBase::incStrong/decStrong` on the object pointer, RefBase at offset 0; `ANativeWindowBuffer` at offset 8; it reads `handle` at offset 60 of `getNativeBuffer()`; it passes `keepOwnership = false`).
- HIDL: allocator and mapper 2.0 (gralloc0 adapters from html6405's `hardware/samsung`), composer 2.1 with AOSP's `HwcLoader`, all passthrough, as on the Galaxy Camera.

Not in the first build: camera (`camera.tegra.so` needs the 5.1 libcamera_client/libgui ABI), the OMX video decoders (`libnvomx`, 5.1 libmedia/OMX ABI), the TLV320AIC325x audio HAL (`audio.primary.tegra.so`, libmedia), sensors (`sensors.macallan.so` + `libinvensense_hal`).

## Partitions

No repartitioning, ever (the GPT sits behind NVIDIA's BCT/PT area).

| GPT | LineageOS use | Size |
|---|---|---|
| LNX | boot | 8 MB |
| APP | system, with vendor inside (`/system/vendor`, `/vendor` a symlink) | 1000 MB |
| CAC | system_ext (stock `/cache`, not needed by LineageOS) | 768 MB |
| UDA | data | ~56 GB |
| SOS | stock Remix OS recovery, untouched | 8 MB |
| MSC | misc | 2 MB |
| USP, MDA, DTB, BMP, LBP, CHG, FBP, FCG | never written | |

**System size**: the Galaxy Camera's LOS21 system is 1120 MB (APEX 277, system_ext 220, product 147, app dexpreopt 57). For 1000 MB the sk1wg build uses `common_mini_tablet_wifionly`, preoptimises only the boot image and system_server, and drops phone, camera, updater and theme packages (`RemovePackages`). That still made 1210 MB (2026-11-07: system_ext 291, APEX 260, product 185 with WebView 90, framework 151, fonts 79), while the vendor files are only 33 MB. So system_ext went to CAC and vendor into system. The linker resolves its `dir.*` paths with `realpath`, so `/system/vendor` binaries still get the vendor namespace; the shims are matched on realpaths, hence the `/system/vendor/...` entries in `TARGET_LD_SHIM_LIBS`.

## Testing without touching Remix OS

`fastboot boot` only loads the kernel and ramdisk. For a full LineageOS boot there are two ways:
1. **Internal eMMC**: flash APP (`fastboot flash system system.img`) and CAC (`fastboot flash cache system_ext.img`). Remix OS's system comes back with `fastboot flash system system.img` from the official 2.0.305 zip, and CAC is only its cache. But LineageOS needs `/data` formatted, which loses Remix OS's data.
2. **microSD** (`SK1WG_SDCARD_ROOT=true`): `rootdir/etc/fstab.macallan.sdcard` mounts system, system_ext and data from the card's partitions 1-3. The eMMC is not written at all. The card is partitioned and written from the mini recovery (`mmcblk1` only).

## First boot procedure (internal eMMC)

Images: `device-dump/lineage-21-2026-11-07/` (`SHA256SUMS` beside them). Battery at 50% or more. The bootloader in "Fastboot Protocol" mode (Volume Up + Power, then pick it in the menu).

1. Zero-risk check first: the cmdline test (`fastboot boot device-dump/test-images/mr-cmdline-test/minirecovery.img`, then look for `sk1wg.cmdline_test=1` in `/proc/cmdline`).
2. Write system and system_ext, then wipe data (loses Remix OS's data):
   ```
   fastboot -S 256M flash system system.img
   fastboot -S 256M flash cache system_ext.img
   fastboot format:ext4 userdata
   ```
   `-S 256M` sends the sparse images in pieces (ours are 1010 and 306 MB; stock's system was 757 MB). `boot` (LNX) is **not** flashed yet.
3. `fastboot boot boot.img`. The build is userdebug with `WITH_ADB_INSECURE`: adbd starts at boot without the key prompt (USB 0955:7100), so `adb -s <serial> logcat` and `dmesg` work even if the display does not. The first boot compiles apps on the device: several minutes.
4. Only once it boots: `fastboot flash boot boot.img`.

Back to Remix OS: `fastboot flash system`, `fastboot flash boot` with the official 2.0.305 images, `fastboot format:ext4 cache`, `fastboot format:ext4 userdata`.

microSD variant: `device-dump/lineage-21-2026-11-07-sdcard/` (same sources, built with `SK1WG_SDCARD_ROOT=true`; only `boot.img` and `system.img` differ). It needs the card partitioned (p1 >= 1000 MB, p2 >= 800 MB, p3 rest) with the raw images on p1/p2 (`simg2img` first) and an empty ext4 on p3, then only `fastboot boot boot.img`. Still open: the mini recovery has no `fdisk` (left out on purpose), so the card is best prepared on the PC (a reader passed to WSL with `usbipd`) or with a partitioning helper that refuses anything but `mmcblk1`.

## Wi-Fi and Bluetooth (2026-11-07, fix19)

- Wi-Fi: bcmdhd built in as module `bcm43341` (parameters under `/sys/module/bcm43341/parameters/`), firmware and NVRAM in `/vendor`. **No vendor Wi-Fi HAL**: this bcmdhd has no nl80211 vendor commands (no `wl_cfgvendor.c`), so `libwifi-hal-bcm` fails "set hal start" and LineageOS's legacy HAL crashed; the AIDL HAL of this tree does not even build against libhardware_legacy's `wifi_hal.h`. Without a HAL the framework drives `wlan0` with wificond and wpa_supplicant (`lib_driver_cmd_bcmdhd`), with stock's overlays (`disable_scan_offload=1`, `p2p_disabled=1`). Scans work. The MAC is NVRAM's placeholder 00:90:4c:11:22:33 (stock had a different one); Android randomises per network anyway.
- Bluetooth: AOSP's Broadcom `libbt-vendor` on `/dev/ttyHS2` (`configs/bluetooth/vnd_sk1wg.txt`), HIDL 1.0 HAL declared in `manifest.xml`. The chip has no address and the HAL aborts without one: `init.sk1wg.bdaddr.sh` makes a random locally administered address on the first boot in `/data/vendor/bluetooth/bdaddr` (`ro.bt.bdaddr_path`). Turns on.
- Wired headphones (fix37, user-confirmed 2026-11-08): the jack is detected (`h2w` switch, reported as a wired headset), but the codec stayed on the speaker with the jack switch off. AudioPolicy moves the open primary output between the speaker and the jack with `createAudioPatch()`/`updateAudioPatch()`, which the emulator HAL only recorded, and every new sink took its route from the address the stream was opened with (the speaker). `DevicePortSink::routeTo()` now applies the patch's sink device at once and later sinks use it: headphones in, `Int Spk Switch` off and `Headphone Jack Switch` on; out, the reverse.
- Bluetooth audio (fix36, user-confirmed 2026-11-08): headphones paired but never connected, because no `bluetooth.profile.*` property was set (A2DP source "Disabled") and there was no BT audio HAL behind `audio.bluetooth.default`. Now `android.hardware.bluetooth.audio@2.0-impl` (loaded by `android.hardware.audio.service`, declared in `manifest.xml`) and the Galaxy Camera's profile list: A2DP source connects with AAC, encoded in software (`A2DP_SOFTWARE_ENCODING_DATAPATH`), and media goes to the headphones. A connect attempt that ends in `PAGE_TIMEOUT` means the headphones are off or busy with another device.
- Internet over Wi-Fi needed one more kernel fix: netd could not add the default route ("Error adding route 0.0.0.0/0 -> 192.168.2.1 wlan0 to table 1007: Network is unreachable") because 3.4's `fib_check_nh()` checked the gateway only through the policy rules, and none of Android's matches that kernel-internal lookup (they need `iif lo`). Upstream 3bfd847203c6 ("net: Use passed in table for nexthop lookups"): look in the route's own table first. Then the network validates (2026-11-07, boot fix20).
- The BCM43341 is 2.4 GHz only (stock never saw a 5 GHz network either).
- No serial console: the bootloader's `console=ttyS0,115200n8` made every kernel message a synchronous UART write; the kernel no longer has `SERIAL_8250_CONSOLE`, the boot command line adds `loglevel=4`, and init stops the debuggable builds' `console` shell (and its notification).

## Audio, backlight, sensors (2026-11-07, fix22)

- Audio: `audio/` is the emulator's tinyalsa-based HIDL 7.1 HAL (`device/generic/goldfish/audio`) renamed `*.sk1wg`, on ALSA card 1 (`tegraaic325x`; card 0 is the HDMI HDA), with stock's `nvaudio_conf.xml` routing applied when a stream opens (speaker: `LOL/LOR Output Mixer`, `Int Spk Switch`, `Speaker Playback Volume` 0x22; headphone: `HPL/HPR Output Mixer`, `Headphone Jack Switch`; mic: `Mic_Bias_Power_ctrl`, `Int Mic Switch`). Speaker and headphone are both on for now. The first builds had **no audio policy configuration**: every stream's volume range was 0..0, so the volume keys only showed the slider at zero. Stock's NVIDIA audio HAL was not used (it links Android 5.1's libmedia).
- Backlight: `lights/` is a small AIDL Lights HAL writing `/sys/class/backlight/pwm-backlight/brightness`. Without it the backlight also stayed on when the screen went to sleep.
- Sensors: stock's Invensense HAL (`sensors.macallan.so` and its MPL libraries) is device API 0.1, and `android.hardware.sensors@1.0-impl` aborts below 1.3 ("getHalDeviceVersion()=0"), which kept the boot from completing. `sensors/sensors_wrapper.c` (`sensors.sk1wg`, selected with `ro.hardware.sensors=sk1wg`) presents it as 1.3: `batch()` becomes `setDelay()`, `flush()` queues the flush-complete event. All 8 hardware sensors are listed.

## Media, microphone, WebView, cover (2026-11-07, fix23-fix29)

- **No sound from apps** while `tinyplay` worked: every MediaCodec start failed with NO_MEMORY ("No ion heap of name system exists"), because Codec2 needs `/dev/dma_heap/system` or `/dev/ion` for its linear buffers and this kernel had neither (macallan uses nvmap). The kernel now registers a system-heap-only ION device (`drivers/gpu/ion/ion_system_only.c`, `CONFIG_ION_SYSTEM_ONLY`), and ueventd makes `/dev/ion` 0664. Codec2's `C2AllocatorIon` and libion speak this kernel's legacy ION ABI. The 3.4 ION core had never been built without `ION_TEGRA` and crashed the tablet four times before it worked: `page_info` allocated with `sizeof(pointer)`, cache sync before `sg_dma_address` was set, `sg_dma_len` never set with `CONFIG_NEED_SG_DMA_LENGTH` ("Bad page state"), cached buffers mapped through a `vm_insert_page()` fault handler ("kernel BUG at mm/memory.c:2733"), and `ION_IOC_MAP` missing. Testing aid: a static program replaying libion's sequence (ALLOC with `ION_FLAG_CACHED`, SHARE, MAP, mmap, write, FREE).
- Microphone: the internal mic is on the codec's left input (the right channel is silent). A mono `pcm_readi()` never returns on this codec, so the HAL always captures stereo and hands out the left channel (`audio/device_port_source.cpp`). Headphone and headset devices now use the codec's PCM too.
- **WebView** (Jelly, and any app with a WebView): on the native ES 2.0 driver Chromium 134 fails to create its Skia `GrContext` ("OOP raster support disabled") and then crashes `VizWebView`; not the extensions (all of Skia's ES 2.0 entry points resolve) and not the odd GLSL string ("OpenGL ES GLSL 1.00", which Skia accepts on Android). Through ANGLE (`--use-gl=angle --use-angle=gles`) it creates the context but pages stayed white: the T114 EGL rejects `eglCreateImageKHR(EGL_GL_TEXTURE_2D_KHR)` with `EGL_BAD_PARAMETER` for any texture that is not mipmap complete (level 0 only with the default `GL_NEAREST_MIPMAP_LINEAR` filter), which is how ANGLE creates its textures. `shims/egl_tegra.c` is now `libEGL_tegra.so` in front of NVIDIA's loader (installed as `libEGL_tegra_nv.so`, also forwarding its private `NvEglInitClientFunctions`/`NvEglRegClientApi` that the GLES loaders call) and retries such images with a non-mipmap filter. Debuggable builds write the ANGLE flags to `/data/local/tmp/webview-command-line` at boot; a user build needs another way. The AHardwareBuffer backing is not available: the EGL has no `EGL_ANDROID_native_fence_sync` (stock had none either, no `CONFIG_SYNC`).
- Keyboard cover: a magnet and a Hall switch on GPIO PK6 (`sw-key`, `SW_LID`, low = closed). Jide's driver only reported "closed" and left "open" to the eDP bridge's power-on, so the lid stayed closed for Android; it now reports both edges. `config_lidControlsSleep` sets `lid_behavior` to SLEEP on a fresh install. PK6 is not a T114 wake pin, so opening the cover does not wake the tablet from LP0 (kept for the battery); the power key does. The keyboard and touchpad work (user-confirmed 2026-11-08).
- No HDMI connector on this tablet (user-checked 2026-11-08): ALSA card 0 (HDA HDMI) and the HDMI display controller are the SoC's, with nothing wired out.
- Boot animation: AOSP's `bootanimation` only uses NPOT textures when the driver advertises `GL_OES_texture_npot`; otherwise it pads them to a power of two but still maps the whole texture onto the quad, so the uninitialised padding showed as noise. ES 2.0 core already allows NPOT with `CLAMP_TO_EDGE` and no mipmaps (all it uses): fixed on a local `sk1wg` branch of `frameworks/base` (fix31, clean).
- Adaptive brightness (fix31): the CM3217's `/dev/lightsensor` was root-only, so `sensors.macallan.so` could not enable it (`LIGHTSENSOR_IOCTL_ENABLE`). Now 0660 system; the HAL reports the raw ADC count as lux, so the overlay uses stock Remix OS's level tables. The driver only reports changes. Confirmed working by the user in daylight (2026-11-08). The node is labelled `device` in SELinux: needs a type before enforcing.
- No hardware double tap to wake: the FocalTech controller (chip ID 0x59, firmware 0x14) ignores writes to the usual gesture registers (0xD0-0xD8).

## Performance (2026-11-07)

- The main cause of the lag was **app code without AOT compilation**: the system partition is full, so `WITH_DEXPREOPT_BOOT_IMG_AND_SYSTEM_SERVER_ONLY` leaves every app at "verify" (JIT only). Settings scroll, 90th percentile frame: 900 ms at "verify", 48 ms after `cmd package compile -m speed`. `init.sk1wg.dexopt.sh` compiles the everyday apps into `/data` after boot.
- Clock scaling: cpuquiet does online cores on demand, but during a scroll the interactive governor stays at `hispeed_freq` (1020 MHz), the EMC drops to 102 MHz and the GPU stays at 240 MHz (of 600). The power HAL (LineageOS libperfmgr, `configs/power/powerhint.json`) holds Tegra's PM QoS nodes (`/dev/cpu_freq_min`, `/dev/min_online_cpus`, ASCII hex values, kept while the fd is open) and the EMC and cbus floors (`/sys/kernel/tegra_floor/*_state`) on touch and app launch. Same scroll with those floors: median 16 ms instead of 24, 90th percentile 32 ms instead of 46.
- Composition: SurfaceFlinger composes every layer on the GPU (CLIENT): NVIDIA's HWC 1.1 puts all layers in the framebuffer with its default `persist.tegra.compositor=surfaceflinger`. Stock ran with `debug.sf.disable_hwc=1` and `persist.tegra.compositor=glcomposer`, so its overlay path was never used either. With `glcomposer` the HWC takes the layers (DEVICE) and frames are faster, but the panel shows garbled content: not usable until the cause is found (possibly the same as the garbled boot animation).
- Fast scrolling (fix30-fix31):
  - **SurfaceFlinger crashed** in `NvGrLock()` (mutex in an unmapped buffer header) from the HWC's `set()` and took the framework down: the mapper's deferred frees (4 handles) were too few when a fling replaces many composer buffer slots. Freed handles now stay registered for at least 1 s (newest 8 always, 64 at most).
  - **The EMC stayed at 102 MHz** during flings: NVIDIA's EMC actmon values (boost above 60% activity in 16 MHz steps, halving each window) never caught the bursty load. With 20/10% thresholds, 10% steps, coefficients 800/90 (`tegra3_actmon.c`): 5-7% late frames instead of 32%, the same as an EMC floor at 792 MHz, and the EMC still idles.
  - **About 1 s stalls** in the app's RenderThread, in `NvGrLock()` waiting on the buffer's cross-process lock (2 s `pthread_cond_timedwait`, woken after ~0.95 s): NVIDIA's HWC keeps the last frame's layer buffers locked until its next `set()`, while SurfaceFlinger waits for the app's next frame. The wait is now 0 (`extract-files.sh`, 0x2846), then the abandoned-lock patch takes it. No visible artefacts.
  - The GPU's devfreq governor is NVIDIA's `pod`, which scales on throughput hints that NVIDIA's own SurfaceFlinger sent (`/dev/tegra-throughput`); Android 14's sends none, so the GPU sits at 240 MHz unless the power HAL's cbus floor holds it during touch. The touch boost lasts 2.5 s after the last input event (`vendor.powerhal.interaction.min`) to cover flings. SurfaceFlinger never sends `DISPLAY_UPDATE_IMMINENT` here.
  - A single-module `m <module>` makes the next `m droid` rebuild most of the tree (about 45000 steps): avoid it between full builds.
  - fix31 after a clean boot (no test mounts): four rounds of rapid flings in Settings, no Davey frames, 4-10% late frames, 90th percentile 21-24 ms, no SurfaceFlinger crash.
- Camera: stock's `camera.tegra.so` is HAL1 (our frameworks keep HAL1) but links some 40 Android 5.1 system libraries (libcamera_client, libgui, libui, libbinder, libskia, libhwui, libmedia...), so it cannot load on Android 14. Findings (2026-11-08):
  - Both cameras are **Toshiba T8EV5** 5 MP YUV SoC sensors (on-chip AE/AWB/AF): stock's log shows `sensor type= 1` with flag 0x04 (back) and 0x05 (front). They share i2c-2 address 0x3c; the board's power-down/reset GPIOs pick one (back PBB5/PBB7 + `vdd_af_cam1` focuser supply + CAM_MCLK, front PBB6/PBB3 + PBB0 as clock). Jide's driver `drivers/media/video/tegra/t8ev5.c` (misc `/dev/t8ev5`, already built and present on LineageOS) holds the tables for 2592x1944, 1280x720, 960x720 and 640x480, AF, flash LED, white balance and exposure. It also auto-detects an alternative MT9P111 module (not fitted here); the separate `mt9p111.c` does not build (missing header) and is not needed.
  - `nvcamera.conf` maps camera0/1 to `/dev/t8ev5` back/front. The CSI port and lane count are not in the kernel: NVIDIA's userspace (`libnvodm_imager`/`libnvmm_camera`) programmed the VI. To be found by trying CSI-A/B with 1/2/4 lanes.
  - The V4L2 soc_camera host `tegra_v4l2_camera.c` (`VIDEO_TEGRA`) does not compile: it is written for the old `nvhost_device` bus, while this tree's nvhost uses `platform_device` + `nvhost_device_data` (roth has the same stale file). It binds to the same `vi` device as nvhost's own VI driver (`drivers/video/tegra/host/vi/vi.c`, which serves `/dev/tegra_camera` to NVIDIA's userspace), so one of the two must go. It was written for Tegra 2/3; T114 may differ (MIPI calibration moved to a separate unit, `/dev/mipi-cal`).
  - AOSP's external camera HAL accepts only MJPEG (and Z16) from V4L2 and reports `LENS_FACING_EXTERNAL`: a copy in the device tree needs YUYV/UYVY input (libyuv) and back/front facing.
  - NVIDIA's camera libraries (`libnvmm_camera.so`, `libnvodm_imager.so`) only need NVIDIA libraries plus libc/libm/libstdc++/libcutils/liblog/libjpeg/EGL/GLES, so they could load on Android 14; only the HAL glue is tied to 5.1. Their NvMM API is undocumented: fallback only.
  - Plan: port the host to the platform-device nvhost API, add a soc_camera subdev wrapper around t8ev5.c (reusing its tables), register the two sensors as soc_camera devices, find the CSI port/lanes, then the HAL. Scope agreed with the user: preview and still photos; video recording left out.
- `ro.opengles.version` declares ES 3.2 (as html6405's Exynos 4 trees do) while the driver is ES 2.0; revisit if an app takes an ES 3 path and fails.

## Code review (2026-11-07, fix32)

Three read-only review agents went over our kernel commits, the graphics shims and HALs, and the rest of the device tree. Fixed:
- **Kernel:**
  - binder secctx size truncation (a 64-bit `buffers_size` truncated to 32 bits put the security context inside the data area: a forged SID);
  - ION: handle races (CVE-2016-9120), size overflows, cached-buffer sync, private mmaps;
  - `sw_keys` probe race;
  - namespace inode numbers leaked on error paths.
- **Device tree:**
  - mapper deferred frees only in SurfaceFlinger and by age;
  - EGL shim error and GL state handling;
  - audio speaker/jack switching, capture close and error handling, 48 kHz only;
  - sensors `batch()` before `activate()`;
  - ueventd duplicate `/dev/ion` rule and 0777 nodes;
  - Wi-Fi Direct permission.

Known and left as they are, for now:
- The gralloc lock-wait patch (0x2846) removes the cross-process buffer lock's mutual exclusion: every contended `NvGrLock()` breaks the lock, and a broken holder's unlock can leave LockState wrong, so later locks break it again. GPU access is still ordered by syncpoint fences; CPU readers/writers of the same buffer could see torn content. The clean fix is to keep NVIDIA's HWC from locking the client-composed layers it never reads.
- Not seen in practice: after a double `NvGrUnregisterBuffer()` the `bne` refcount patch can leak a buffer.
- `vendor.powerhal` floors and the actmon tuning race the EMC to its maximum under load: check the battery drain.
- The sensors wrapper only returns flush-complete events from the next `poll()`; with only an on-change sensor active a flush can wait.
- No SoftAP: with no Wi-Fi HAL nothing switches bcmdhd to the AP firmware.
- The headset mic is never selected (`Ext Mic Switch`), so the internal mic always records.
- Before SELinux enforcing:
  - the dexopt script (vendor calling `cmd package`) must move to system_ext or be replaced;
  - new device nodes need types (`/dev/ion`, `/dev/lightsensor`, the PM QoS nodes, `tegra_floor`, the backlight);
  - this kernel has no SELinux binder hooks at all.
- Kernel follow-ups:
  - binder secctx from `proc->cred` instead of the task;
  - upstream 4ce5d2b1a8fd (ns-file bind mounts across mount namespaces).

## Stress test (2026-11-08, fix32 system)

52 minutes of CPU, memory, storage, UI, screen off/on and media load. No reboot, panic, WARN/BUG, tombstone, ANR or crash, and system_server, surfaceflinger and the media processes kept their pids.

- **ION leak, fixed in fix33** (kernel "ion: hand userspace handle ids, not kernel addresses"): each audio playback kept 512 KiB in both media.swcodec's and mediaserver's ION clients for good. The 3.4 core handed userspace the handle's kernel address, negative as libion's `int` handle, and C2AllocatorIon only calls `ion_free()` on handles >= 0. Handles are now small ids in a per-client idr, as upstream since 3.10. Verified on fix33: 512 KiB during a playback, 0 after it and after 10 playbacks.
- Thermal: 4 busy cores reach the 90 °C passive trip in about 95 s at the 1606.5 MHz EDP cap; sustained 2-thread load sits at 76-86 °C without frequency throttling, and cpuquiet keeps all 4 cores online. `therm_est` (skin estimate) reads 16-30 °C while the CPU is at 90 °C, so the skin cooling device never engages. **Same as stock** (2026-11-08): the same 4-core burn in the RAM-booted mini recovery, with the same CPU policy on both kernels (interactive, cpuquiet runnable; without Android, stock's default governor is userspace at 510 MHz), ran all 4 cores at 1606.5 MHz on stock 3.4.108 too, hit 92 °C in 35 s (ours in 20 s, starting from a tablet still warm from the stock run), throttled through tegra-balanced at the same 90 °C trip, and stock's `therm_est` read 21-26 °C as well. Not a regression; left as is.
- Memory: no zram; one WebView renderer reached 665 MB PSS with about 20 tabs, the lowmemorykiller then killed cached apps and launches took 3-6.6 s. **zram fixed in fix34**: the fstab already had it, but fs_mgr writes `max_comp_streams` (default 0) first, 3.4's zram has no such attribute, and swapon_all gave up. `max_comp_streams=-1` skips the write; zram is now half the RAM (936 MB) with swappiness 100. The same kind of load then compressed about 3.2:1 and killed no app. No memtrack: dumpsys shows "Graphics: 0" (nvmap holds 100-170 MB for the launcher).
- Storage (/data): 42 MB/s write with fsync, 117 MB/s read, no mmc errors.
- Flings: Settings 6-12 % janky (p90 22-27 ms), WebView pages about 35 fps (19 % janky).
- Screen off/on, 20 cycles: the display came back every time. 2 of 20 wakes logged the SN65DSI86 bridge's `link training write error` (no retry in the driver), each wake logs 8 i2c NAKs from the bridge at 0x2c, and the dock keyboard re-enumerates on every off/on. That last one is Jide's design, kept: `drivers/switch/switch_adc.c` (the Palmas GPADC dock detection) cuts the keyboard's 5 V (GPIO PO3) on FB_BLANK and turns it back on at unblank, so the keyboard draws nothing while the screen is off, cannot wake the tablet, and needs about half a second to enumerate after a wake. The bridge training check got a wait and retry in fix35 ("sn65dsi86: wait for eDP link training, retry it"), and the binder ioctl noise is gone in fix35 (GET_NODE_INFO_FOR_REF implemented, ENABLE_ONEWAY_SPAM_DETECTION accepted).
- Log noise: servicemanager's BINDER_GET_NODE_INFO_FOR_REF and every process's BINDER_ENABLE_ONEWAY_SPAM_DETECTION return -EINVAL and are logged; together with healthd they cut the dmesg window to about 35 minutes.
- Minor: order-5 allocation failures in seq_read (nvmap debugfs), NetworkStats `Null bpf map` WTFs on every foreground change (no eBPF), libprocessgroup cannot create `/sys/fs/cgroup/uid_N`, battery temperature reads 0.0.

The release mini recovery (our kernel, 2026-11-08) was RAM-booted: adb, `su`, `rootrun`, `backup-critical` (106 MB into RAM) and `rootrun reboot-to bootloader` work.
